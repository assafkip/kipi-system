## What changed

**`linear-worker.sh`** -- the picker publishes a separate `rework` set (owner:sana, not owner:assaf, has a DoR, state type `started`). Disjoint from the fresh set by construction: folding a started issue into `ready` would send it down the fresh-work path, which cuts a worktree from `origin/main` and would blow away the PR's commits (the `BASE` block). Announced in DRY mode only -- that is the seam `kipi-dispatch.sh` reads. The apply loop is untouched; a rework round is still reached the way it always was, through `--issue ASK-n` from converge. The `--issue` path is byte-identical to before.

**`kipi-dispatch.sh`** -- one `ps` snapshot taken before candidate selection and reused by both guards. Rework is a fallback, never a peer: fresh work wins outright, so the backlog cannot starve behind a PR that keeps going red. A candidate with a live converge is passed over rather than exiting, so one permanently-live run cannot hide every other stranded issue behind it. A rework dispatch fetches `origin` first.

**The rework prompt** now opens with a rebase onto current `origin/main`.

## Budget (loop-exit 7), stated

Rework spends the same `KIPI_DISPATCH_DAILY_MAX` allowance as fresh work; the daily cap is not raised. `MAX_ATTEMPTS` is applied **at the announcement**, not left to the work loop: leaving it there means a permanently-red PR spends a budget slot and a converge launch every heartbeat before the refusal fires. Case A6 pins that.

## Deviation from the DoR, and the evidence for it

The DoR says `kipi-dispatch.sh` "fetches and rebases onto `origin/main` first". It **fetches**. It does **not** rebase the worktree, because that would break the worker:

`position_tree_on_pr_head` refuses any tree holding commits reachable from neither `origin/<branch>` nor `origin/main` (`linear-worker.sh:528`). A rebase rewrites shas, so a dispatch-side rebase produces exactly that state -- `tree_holds_pr_head` goes false, `position_tree_on_pr_head` refuses with "the tree holds N commit(s) that exist nowhere else", and the issue stalls for a human. Two writers on one worktree is the defect class this repo keeps closing.

So the rebase reaches the agent through the rework prompt, inside the tree it can also push from. Same outcome, one writer.
