proposed title: Isolate per-item failures in every batch stage

**The failure shape**

A stage loops over a batch and calls something fallible per item (parsing, subprocess, deserialization, network, model output). One item raises, the exception unwinds the whole loop, and the stage returns zero rows. Every item that would have succeeded is dropped with no record it existed. Downstream, an empty result looks identical to "there was nothing to do," so the outage is silent.

**Why it survives review**

Isolation usually gets added only to the stage where a failure was first observed, typically the final delivery step. The earlier stage that builds or prepares the batch stays a straight loop. Each stage reads fine on its own; the asymmetry is only visible when you read the two side by side and notice one is fail-soft and the other fail-hard.

**How to apply**

1. Inventory every stage that iterates a batch and calls anything fallible. Fallible includes any call that can raise an exception subclass you did not explicitly enumerate.
2. Put the guard inside the loop body, wrapped around the smallest fallible unit. Catch the base class that covers the whole family (parse errors are often subclasses of a broader error type, so catching the narrow one misses siblings). Record item identifier plus error, then continue.
3. Return the partial batch together with a failure count. Never return an empty batch when items were attempted. The count is the only thing that separates "empty" from "broken."
4. Alarm on zero output from a stage that had input. Isolation without this just converts a loud abort into a quiet one.
5. Reproducer first: inject one poisoned item into a batch of good ones, assert the good ones still come out and the bad one is recorded. Keep it as a regression test so the guard cannot be refactored away.

**Boundary**

Per-item isolation is wrong when items are not independent: a transactional batch, or an ordered pipeline where later items depend on earlier ones. There the correct behavior is to fail the batch atomically and loudly. Decide which kind each stage is and state it in the code, so the next reader does not guess.
