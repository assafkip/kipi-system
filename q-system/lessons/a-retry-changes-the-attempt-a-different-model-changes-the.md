title: A retry changes the attempt, a different model changes the reasoning
date: 2026-08-02
---

A loop detector usually has exactly two terminal outcomes: refuse the call, or let it through with a nudge. Neither one changes the reasoning that produced the loop, so a pattern that deadlocks a model deadlocks it again on the very next attempt, and the detector's only real function becomes deciding how many times to watch the same failure. The missing third outcome is to hand the situation to a DIFFERENT model in a session that shares no history, ask it for a diagnosis rather than a fix, and staple the answer to the refusal. Failure distributions across models are complementary, so a pattern that sits inside one model's blind spot usually sits outside the other's. This is a branch on the detector that already exists, not a new detector, and it should be built that way: one tagged call site, one subprocess, one test file.

Three design constraints decide whether it helps or hurts. First, escalate only where the run has ALREADY stopped. A refusal is the right moment because the seconds a triage costs were lost anyway; a warning tier is the wrong moment because most runs recover unaided, and a path where a human is waiting for a reply is the worst moment of all, since there the latency is paid by the person. Second, which refusals count is declared at the call site, never inferred from the message text: a policy refusal and a rate-limit refusal are not stuck states, and no amount of cross-model triage repairs an environment. Third, the second opinion is an INFERENCE, not a measurement, so require it to return the command that would refute its own diagnosis and store it labelled as a proposal.

Two failure modes are easy to ship by accident. The escalation must be incapable of withholding the refusal it decorates: a missing dependency, a dead endpoint, a timeout, and a malformed reply all have to degrade to the original behaviour byte for byte, because a fail-closed detector whose own helper is broken blocks the repair too. Prove that with a literal expected string rather than by comparing against a baseline captured through the same code, since a change that moves both sides is invisible to a same-as-baseline assertion. The other one is cost: the moment a test suite can drive the detector into its stuck state, that suite starts billing real model calls. Stubbing each suite that does it today fixes only the suites someone remembered, only on the branches that carry the stub. Put the refusal at the single place that spawns the process, keyed on a signal that is true in every test run and false in every production run, and every suite written afterwards inherits it without knowing it exists.
