## 1. READ THIS FIRST — do not merge PR #23

**PR #23 (ASK-210) adds a merge gate that no Linear-flow PR can ever satisfy.
Merging it stops every future agent PR from landing, permanently.**

`pr-receipt-gate.py` refuses any `sana/ask-<n>` PR without a prd-os receipt.
Receipts are written only by `issue_runner.py close`. That runner refuses to load
any spec whose first body line is not a `prd_split.py` provenance marker:

```
$ python3 plugins/kipi-dsse/scripts/issue_runner.py load ASK-211
issue spec rejected: marker not generated by prd_split.py
```

Linear issues have no parent PRD, so no legitimate spec can exist for them, so
`close` can never run, so the gate blocks 100% of its target population forever.

Verified by hand on 2026-07-27: a well-formed spec was written for ASK-211 and
`load` refused it on provenance. The spec was then deleted rather than stamped
with a forged marker. **Do not forge that marker.** Defeating the guard is the
one move this repo exists to prevent.

The adversarial reviewer approved PR #23 without catching this. Captured as
`sp-64511091`.

**Fix before #23 merges. Three routes, pick one and say why:**
1. `prd_split.py` gains a Linear-DoR entry point (generates a spec with a real marker)
2. the marker guard accepts a second declared provenance (e.g. `linear-worker`)
3. the gate proves done differently for Linear work

Route 1 is the one the merge-authority design already argued for (item 6b) — it
also gives `issue_runner.py scope <path>` to Linear work for free, which answers
problem 4's open question about out-of-scope edits. Read that argument before
picking.
